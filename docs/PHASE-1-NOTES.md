# Phase 1 — build notes

Exit criterion from the spec: _"every content type round-trips CMS → typed
query → rendered component."_

The code half of that round trip is built and verified. The live half needs a
Sanity project, which requires your account — see
[Connect your Sanity project](#connect-your-sanity-project) below; it takes
about five minutes.

**Typegen offline fallback:** `sanity schema extract` boots the Studio
workspace, which needs a real project id (a placeholder throws before
extracting). `scripts/typegen.mjs` therefore extracts only when
`NEXT_PUBLIC_SANITY_PROJECT_ID` is set and otherwise falls back to the
committed `.sanity/schema.json`. After schema changes, run typegen with the
project configured and commit both files.

## Decisions that deviate from the spec, with reasons

### 1. Studio v4 (as specced) — but v5/v6 is blocked by Next 15, not by choice

Sanity Studio ≥ 5 uses React 19.2's `useEffectEvent`. Next 15 bundles its own
vendored React for app-router builds which doesn't expose it, so Studio v5+
only works on Next 16 (that's also why `next-sanity` v12+ requires Next 16).
Pinned: `sanity@4.22`, `@sanity/vision@4.22`, `next-sanity@11`. When Phase 8
(or later) upgrades to Next 16, bump all three together.
React itself moved 19.1.1 → 19.2.8 (required by the Sanity toolchain; Next
15.5 supports it).

### 2. Footnotes are inline objects, not block-level

A footnote annotates a point in a sentence. Modelling it inline (inside block
children) records that point, which is what lets Phase 2 place the margin
note at the reference's vertical offset. Block-level footnotes would lose the
anchor forever. Phase 1 renders them as a numbered marker + inline note
(phrasing content only — `<details>` is invalid inside `<p>`; the render test
caught exactly that).

### 3. `caseStudy` has no `kind`, `category` or generic `body`

§3.3 says "everything in `post` except kind/category" — the §6.6 template
sections (background/problem/process/implementation/outcomes) ARE the body,
so a parallel generic body field would be a second source of truth. `series`
was also omitted: case studies aren't serialised. Derived fields concatenate
the four prose sections plus process step bodies.

### 4. `embed` renders as a link card, not an iframe

§1.8 bans blocking third-party requests on reading pages; an iframe embed is
exactly that. The card carries title, caption and host. If a genuine player
is ever needed it becomes a Phase 7 decision with a consent story.

### 5. "Open preview" passes no secret

The Studio bundle is public JavaScript; a preview secret embedded in it would
let anyone read drafts. The action sends type + slug only; the Phase 2
`/api/preview/enable` route must authorise by Sanity session (or a
server-side token exchange), not by a bundle-embedded secret.

### 6. Seed covers are generated SVGs

Real photography can't be seeded honestly. The script generates 1200×630 SVG
placeholders, uploads them as assets, and carries on without images if the
upload fails. Replace them with real covers as content gets written.

## Connect your Sanity project

1. `npx sanity login`, then `npx sanity projects create` — or create one at
   [sanity.io/manage](https://www.sanity.io/manage). Create a dataset named
   `development`.
2. Copy `.env.example` → `.env.local`, fill `NEXT_PUBLIC_SANITY_PROJECT_ID`,
   and add a write token (`SANITY_API_WRITE_TOKEN`, Editor role) for seeding.
3. In the project's API settings, add `http://localhost:3000` to CORS origins
   (with credentials).
4. `npm run seed` — writes the development dataset (idempotent, `seed-*` ids).
5. `npm run dev` → open `/studio`, sign in, and check: Needs attention shows
   empty queues, Journal groups by month, Tags show usage counts.
6. Publish any seeded post after an edit — the Derived tab should update
   (reading time, word count, plain text, headings).

## Not built yet, deliberately

- `/api/preview/{enable,disable}` — Phase 2 (draftMode + banner). The Studio
  action already points at it.
- `/api/revalidate` webhook — Phase 7; until then published pages use the
  3600s ISR safety net baked into `sanityFetch`.
- Public pages consuming the queries — Phase 2 (`/writing/[slug]`, journal)
  and Phase 3 (indexes, home). The two Phase 0 verification routes still
  stand in.
- Postgres/Drizzle — Phase 5, per the roadmap (P2 mentions it early; the
  roadmap owns sequencing).

## Before starting Phase 2

1. Do the "Connect your Sanity project" list above — Phase 2 designs against
   the seeded content.
2. Skim a seeded post in Vision (`*[_type == "post"][0]`) to see the shape the
   article template will receive.
3. Decide the preview authorisation model (Sanity session check vs. secret
   exchange) before building `/api/preview/enable`.
